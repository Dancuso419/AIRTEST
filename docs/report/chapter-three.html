CHAPTER THREE

METHODOLOGY AND SYSTEM DESIGN

3.0 Overview

This chapter presents the software engineering research methodology, development lifecycle models, fact-finding techniques, hardware/software technical specifications, ethical considerations, requirements specifications, and comprehensive system design artifacts for the AIRTEST (Airtime Telemetry and Efficiency Stress Test) framework. The system combines a deterministic discrete-event simulation engine built on Network Simulator 3 (NS-3 3.42) with an interactive web visual analytics platform built using React 19, Vite, and Recharts.

3.1 Methodology

The research methodology adopted for the AIRTEST project combines quantitative discrete-event simulation engineering with empirical visual analytics. Evaluating high-density wireless local area network (WLAN) performance in physical campus auditoriums introduces uncontrollable environmental variables, such as background RF interference from neighboring departments, rogue access points, and dynamic physical obstruction. Consequently, discrete-event simulation was selected as the core quantitative research instrument.

The overall research methodology follows a five-stage quantitative execution pipeline:

  1. Parameter Formulation: Defining physical lecture theatre dimensions (15m × 20m), AP deployment coordinates (1-AP centralized vs 3-AP multi-cell), client station densities (10, 14, and 20 active stations), and traffic profiles (Web, Video Streaming, Bulk FTP).
  2. Simulation Execution: Constructing and compiling C++ scenario code (`lecture-theatre.cc`) under NS-3 3.42, orchestrated via an automated Python batch execution script (`run_matrix.py`) across two randomized seeds for a total of 72 simulation runs.
  3. Telemetry Extraction: Intercepting flow-level packet statistics via the NS-3 `FlowMonitor` XML engine to record offered load, received bit rate, delay sum, jitter, and packet loss ratio across all active simulation nodes.
  4. Data Parsing and Transformation: Programmatically processing XML trace logs using Python (`parse.py`) into a structured, validated `results.json` dataset containing calculated airtime utilization and protocol efficiency ratios.
  5. Visual Analytics: Rendering real-time aircraft cockpit instrument dials and responsive stress degradation curves within a custom web application built with React 19, Vite, and Recharts.

3.2 Development Method

Selecting an appropriate Software Development Life Cycle (SDLC) model ensures structured execution, predictability, and software quality. This section evaluates four major development methodologies before justifying the selection of the Waterfall Model for the AIRTEST project.

3.2.1 Waterfall Model

The Waterfall Model is a classic linear, sequential software engineering paradigm introduced by Winston Royce in 1970. It divides the software development process into distinct, non-overlapping phases: Requirements Engineering, System Design, Implementation, Integration and Testing, and Deployment/Maintenance. Progress flows systematically downwards from one phase to the next. Each phase must be fully completed, verified, and documented before the subsequent phase commences.

Table 3.1: Sequential Phases of the Waterfall Model

Phase Name Core Engineering Activities Delivered Artifacts
1. Requirements Analysis Gathering technical specifications, physical space constraints, and performance metrics. Software Requirements Specification (SRS)
2. System Design Defining C++ simulation topology, FlowMonitor schemas, UML diagrams, and React UI layout. Architecture Diagrams, DFD, CFD, JSON Schema
3. Implementation Writing NS-3 C++ scenario, Python batch orchestrator, XML parser, and React frontend. Source Code Base (`lecture-theatre.cc`, `parse.py`, UI)
4. Testing & Verification Executing automated unit tests, integration tests, and full 72-run matrix verification. Test Traceability Matrix & Test Reports
5. Deployment & Maintenance Packaging static JSON dataset and bundling web dashboard for production review. Final Delivered System & Documentation

3.2.2 Incremental Model

The Incremental Model breaks the system down into small, manageable builds. Each increment delivers a functional subset of software requirements. Subsequent increments add new feature modules until the entire system is complete. While effective for commercial software with evolving scope, it introduces overhead when simulation scenarios require a fixed, consistent mathematical model from inception.

3.2.3 Iterative Model

The Iterative Model emphasizes cyclic development, starting with a simple implementation of a subset of software requirements and iteratively enhancing the evolving versions. It relies on continuous feedback loops to refine system specifications throughout the lifecycle.

3.2.4 Prototype Model

The Prototype Model focuses on building an early working demonstration (prototype) of the system to gather user feedback before developing the final software solution. It is ideal for applications where user requirements are highly ambiguous or poorly defined.

3.3 Proposed Model (Waterfall Model Justification)

The Waterfall Model was selected as the proposed methodology for the AIRTEST project. The rationale for this selection is rooted in the mathematical nature of network simulation engineering:

  • Fixed Experimental Parameters: Simulation experiments require strictly defined physical constraints (15m × 20m hall, 80 MHz channel, LogDistance propagation) established before running C++ scenario models. Changes to protocol parameters mid-experiment would invalidate cross-scenario comparative integrity.
  • Strict Pipeline Dependencies: The development steps follow a rigid sequential dependency: the C++ simulation (`lecture-theatre.cc`) must be fully designed and executed before the Python telemetry parser (`parse.py`) can extract FlowMonitor XML traces, which in turn must produce `results.json` before the React dashboard can render visual gauges.
  • Predictable Verification Milestones: The linear progression allowed rigorous verification at each stage: validating NS-3 3.42 C++ compilation before initiating the 72-run scenario matrix, and validating JSON schema formatting before rendering UI components.

3.4 Fact-Finding Techniques

To ensure realistic simulation modeling and user-centric dashboard design, three fact-finding techniques were employed:

3.4.1 Observation

Direct observation of wireless network performance was conducted during peak lecture hours in a 200-seat campus auditorium. Observations revealed that during interactive online quizzes, over 80% of students experienced latency delays exceeding 250 ms, with frequent disconnection prompts. Physical inspection confirmed that while signal strength (RSSI) remained adequate (-65 dBm), channel airtime was saturated due to legacy 802.11ac CSMA/CA contention.

3.4.2 Interview

Structured technical interviews were conducted with Senior University Campus Network Administrators. Key takeaways included:

  • Administrators highlighted that financial approval for enterprise Wi-Fi 6 AP upgrades requires hard empirical evidence showing airtime capacity improvements under heavy student density.
  • Administrators expressed frustration with traditional diagnostic tools that display static tables, stating a strong preference for visual dual-needle instrument gauges comparing Wi-Fi 5 and Wi-Fi 6 side-by-side.

3.4.3 Data Analysis

Existing network traffic logs and IEEE 802.11ac/ax protocol standard specifications were analyzed to determine realistic packet payload sizes. Traffic was categorized into three representative profiles: Web Traffic (exponential 512-byte bursts), Video Streaming (constant 1.5 Mbps UDP stream), and Bulk FTP (continuous 1024-byte TCP packets).

3.6 Ethical Considerations

The AIRTEST project was conducted in strict adherence to academic research ethics standards:

  • Synthetic Simulation Data: All network traffic traces were generated artificially within the deterministic NS-3 discrete-event simulator. No real user network traffic, private communications, MAC addresses, or personal identifiable information (PII) were intercepted or stored.
  • Transparent Methodology: Simulation scripts, random seed configurations, and parsing logic are fully documented and open for peer review to ensure scientific reproducibility.

3.7 Requirement Analysis

Requirements analysis identified the functional capabilities needed to deliver a robust simulation and diagnostic environment. Requirements are divided into Functional Specifications (what the system must do) and Non-Functional Specifications (how well the system performs).

3.8 Requirements Specifications

3.8.1 Functional Requirements

  • FR-01 (Multi-Protocol Simulation): System must execute discrete-event network simulations comparing IEEE 802.11ac (Wi-Fi 5) and IEEE 802.11ax (Wi-Fi 6) under identical physical parameters.
  • FR-02 (Parameter Matrix Orchestration): System must systematically vary client densities (10, 14, 20 nodes), topologies (1-AP, 3-AP), and traffic profiles (Web, Video, Bulk).
  • FR-03 (Automated Log Parsing): System must parse raw FlowMonitor XML logs to extract offered load, achieved throughput, delay sum, jitter, packet loss, and airtime utilization.
  • FR-04 (Interactive Cockpit Dashboard): Web interface must render dual-needle analog gauges comparing Wi-Fi 5 (white needle) and Wi-Fi 6 (green needle) metrics simultaneously.
  • FR-05 (Density Stress Curves): Interface must display responsive line charts illustrating performance degradation curves as client density scales from 10 to 20 nodes.
  • FR-06 (Diagnostic Telemetry Cards): Interface must provide detailed protocol diagnostic cards highlighting airtime savings percentages and spatial reuse efficiency.

3.8.2 Non-Functional Requirements

  • NFR-01 (Deterministic Reproducibility): Simulation pipeline must yield identical numeric results when executed with matching scenario parameters and random seeds.
  • NFR-02 (Dashboard Load Speed): Web interface must load static telemetry datasets and render cockpit gauges in under 1.5 seconds on minimum client hardware.
  • NFR-03 (UI Responsiveness): Gauge animations and metric switches must maintain 60 frames per second (FPS) rendering performance without memory leaks.
  • NFR-04 (Cross-Browser Compatibility): Web application must function seamlessly across major modern web browsers without requiring external plugins.
  • NFR-05 (Data Integrity): Telemetry parser must execute schema validation checks to prevent division-by-zero or NaN values in final JSON outputs.
